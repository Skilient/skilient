Also messaging: venture group threads (they follow work's ventures and members through events), the chat half of sharing (`share_targets`, `share_post`, `undo_share`; `share_post` asks content's `VisiblePosts` batch for the post, never a per-thread call), and the messages' images as paths (the bucket `chat-media` becomes the media service's, W9). Names repeat across versions: rows are keyed by the latest definition; `send_message`, `thread_messages`, `my_threads`, `thread_people`, `dm_blocked`, `toggle_reaction` and `get_or_create_dm` have several, noted per row.

**Messaging tables on the current stack** (all in `public`): `chat_threads`, `chat_thread_members`, `chat_messages`, `message_reactions`, `chat_pins` (5). Columns written by other services' flows: `chat_threads.org_id`, `closed_at` (market, `20261014000000_recruiter_talent.sql:170`), `chat_threads.fair_id` (market, `20261020000000_uni_fairs.sql:397`), `chat_messages.removed_by` (trust, `20260929070000_reports.sql:113`); all four become messaging's columns (see Unclear). Not messaging's: the private bucket `chat-media` and `storage.objects` policies (media, W9), `profiles.chat_read_receipts` (people), `link_previews` (content), `notifications` (notify).

### Realtime

Supabase Realtime did two jobs for chat: the `postgres_changes` stream of new messages (the `supabase_realtime` publication, filtered per member by row-level security) and a private broadcast channel `thread:{id}` for typing and "something changed" pings (policies on `realtime.messages`). Both become the `realtime` platform service (W4): one socket per visible tab, topics `user:{id}`, `thread:{id}`, `event:{id}`; `realtime` asks messaging whether a user may listen to `thread:{id}` (cached 60 seconds); messaging sends `NOTIFY` with the topic and the message inside the transaction that wrote it.
